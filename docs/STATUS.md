## 並列化は効かない（重要）

日を3並列にして流したところ、**3.4時間かけて1日ぶんも終わらなかった**。
そのときの python プロセス23個の CPU 時間の合計は180秒で、ほぼ全部が待ち時間。
同じ時刻に単独の接続で計測すると 2.5 MB/s 出ていたので、回線の問題ではなく
**GitHub 側が同一 IP からの同時ダウンロードを絞っている**と見られる。

`fetch_range.py` の `--concurrency` は既定1（逐次）にしてある。上げてはいけない。

この過程で、書きかけの Parquet が残ると `fetch_range.py` の
「出力があればその日は飛ばす」判定をすり抜けて欠測のまま先へ進む問題が見つかった。
`.part` へ書いて完了時に改名する方式に修正済み。

## 期間の見積り

処理は CPU ではなく**ネットワーク律速**（単日実測 5.8 MB/s、ただし時間帯で変動する）。

| 期間 | DL量 | 逐次での所要時間 | 出力（全国） |
|---|---|---|---|
| 1日 | 2.15 GiB | 6分 | 48 MiB |
| 1週間 | 15 GiB | 45分 | 340 MiB |
| 1か月 | 65 GiB | **3.2時間** | 1.4 GiB |
| 1年 | 785 GiB | 39時間 | 17 GiB |

並列化で縮めることはできない（前節）。所要時間はダウンロード速度がそのまま効く。

### メッシュ（`build_mesh.py`）

500m メッシュ（4次）で 626,992個、16.9 MiB。
1メッシュあたりの観測点は中央値1点、p99 26点、最大 45,651点。

東京 R=80km で上位を見ると、**すべて羽田空港（139.78, 35.55付近）**で

`--airborne-only` で落とせる。

メッシュコードの計算はビットシフト方式で、桁を順に剥がす伝統的な計算と
4,004点 × 4レベルで突き合わせて全一致を確認済み
（東京駅 = `53394611` / `533946113`）。
